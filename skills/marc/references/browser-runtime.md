# Browser runtime and tool selection

Prove the affected user outcome against the captured PR source. A stopped local app or an unavailable browser tool is a setup condition to resolve, not by itself a completed blocked gate.

## Acquire a runtime

1. Inspect the expected URL/port (from consumer browser guidance), listener and process ownership. Check readiness and establish build provenance from a trusted build/launch record or deployment artifact bound to the full source SHA. A branch name, working-tree HEAD, healthy response or existing login alone does not establish which binaries are running.
2. Reuse a healthy runtime with matching provenance and an appropriate data environment. Preserve every pre-existing process. If the expected port belongs to another service or source version, allocate a separate free port; do not stop or replace it.
3. If no matching runtime exists, discover available isolated execution: an existing container engine, VM or approved isolated runner. Build/publish the captured source and start the required services there using repository startup guidance. Use an external build root, bounded readiness waits and sanitized startup logs. Do not assume an absent listener means startup is unavailable; attempt the usable provisioning path and record its outcome.
4. Keep candidate execution separate from developer Git/cloud credentials and unrelated secrets. A separate checkout or an environment-variable cleanup is not a sandbox. Use only the environment and data-access scope explicitly authorized in the consumer browser guidance. Supply required settings through a private run-owned channel, never a whole developer secret store or logged command arguments. Verify the target without printing credentials. Do not provision paid/shared deployments or mutate shared data as a setup fallback. If the required isolated executor or configuration is unavailable, record the exact missing prerequisite and capability probes.
5. Record source SHA, build/artifact identity, URL, data environment, readiness evidence, ownership and cleanup method in the external run record. Stop only run-owned processes/resources, including after a failed check. Never label an unrelated staging deployment as the reviewed source.

### Optional ASP.NET UI-only host

For UI journeys that do not exercise background processing, use the trusted opt-in harness in the MARC bundle at `src/quality/browser-host/Marc.BrowserHost.csproj`. Build it to the external artifact root, mount only its output read-only in the isolated app, and set `DOTNET_STARTUP_HOOKS` to its `Marc.BrowserHost.dll` and `MARC_BROWSER_UI_ONLY=1`. Do not mount developer directories or use a candidate-supplied hook. The harness removes background `IHostedService` registrations (including factories), preserving the HTTP host and ordinary application service registrations. It avoids running graph schema setup, reconciliation, mail and other hosted jobs just to inspect a page. It does not suppress user-triggered operations; scope those separately.

Verify the startup log contains `MARC UI harness applied` and retain the omitted-service identities, hook source/hash, application binary hash and startup configuration names without secrets. Run `src/quality/browser-host/Test-BrowserHost.ps1 -ArtifactsPath <resolved-external-path>` when changing the harness; it checks HTTP and ordinary services remain functional, direct/factory workers are omitted when enabled, and opt-out preserves normal worker execution. The legacy `COQ_BROWSER_UI_ONLY` opt-in is accepted only when `MARC_BROWSER_UI_ONLY` is absent; an explicit MARC value takes precedence. The smoke check covers both names and explicit opt-out precedence. This is scoped UI evidence, not validation of the omitted workers. If the journey depends on a worker or required initialization, choose an appropriately authorized runtime instead of treating a harness-induced failure as a PR defect.

## Select identity and tool

Choose the smallest journey that covers the changed behavior and its affected callers. Select the required application roles from consumer guidance and use separate sessions for different actors. Verify the effective account, tenant and permissions before checking the behavior; one administrator role does not establish another.

Prefer the user's designated normal test account for the required role, using the current task or private automation configuration. Do not automatically substitute an account from an unrelated test journey. Inspect that account's existing representative records before declaring a coverage gap or proposing synthetic fixtures. Keep account addresses in private run configuration rather than publishing them in repository instructions.

For unattended MARC, use the consumer's approved test authentication path when suitable, with designated accounts and actual application permissions. Test authentication does not establish that the normal sign-in provider works. Interactive verification may use an existing authorized login. Missing accounts or login challenges require a precise prerequisite. Connection authorization does not authorize arbitrary data changes: reuse suitable records, seed only authorized prerequisites, and distinguish setup from UI actions. Do not perform real payment, mail or production operations as fixture setup.

Choose the available tool best suited to the assertions: existing Playwright tests for repeatable journeys, gstack browser controls for interactive DOM-driven checks, or available browser/computer-use controls for exploratory/visual interaction. Follow current user instructions and the consumer's tool policy. Probe capabilities on the current machine; do not assume computer use is blocked or require Playwright exclusively. If the selected tool is unavailable, try another suitable available tool before recording a tooling block. A product assertion failure is not a reason to switch tools until it passes. Native desktop control and browser control are separate capabilities.

All tools have the same evidence standard: observed expected/actual outcomes, source-bound runtime, verified persona, meaningful waits, and sanitized screenshots/traces or equivalent observations. Source review, a login, or a screenshot of an unrelated page is insufficient. Save tool choice, unavailable alternatives, setup attempts, checkpoints reached and unreached, and cleanup outcome with the browser gate.

Scope browser assertions alongside the existing exact-source CI coverage. Prove representative changed UI behavior and its integration; do not mechanically recreate every pure-helper input permutation already covered by meaningful unit tests. Record unexercised cases and whether they are material browser gaps or supported by other evidence. A missing required user-outcome check remains blocked; missing exhaustive duplication alone does not require new staging fixtures.

## Resume a held check

An explicit retry or resolved runtime/login/tool prerequisite may rerun the browser gate even if source/base/policy are unchanged. Keep the old blocked report immutable and record the retry externally. Reuse other gates only when their captured identities still match; a browser-only retry is not a fresh approval of changed source or base. Do not merge as part of a user request limited to browser verification. A genuinely changed assessment may receive a new timestamped report; an unchanged block does not need another report commit.

Before excluding completed holds from queue selection, inspect browser-blocked ledger entries for an explicit retry or a changed prerequisite. Use a cheap check of the previously missing capability/configuration, record its state, and retry only when it changes or the user requests it. Do not repeatedly rebuild on an unchanged scheduled hold, or allow completed-key deduplication to suppress an explicitly requested browser retry.
