# Captain guarded actions

Load these procedures before CI recovery, repair, report publication or merge.

## CI recovery and report CI reuse

Run `node <MARC-bundle>/src/quality/marc.cjs --repo <trusted-consumer-checkout> recover-ci <current-capture.json> [investigation.json]` from the trusted controller. It rechecks current source/base/policy, producer registration and CI, then reserves one recovery request total (dispatch or rerun) per PR/head in the resolved `ciRecoveryDirectory`, exclusively creating and flushing a `.request.json` file before contacting GitHub. Dispatch uses the verified PR branch with no source override; collection checks the resulting run's `head_sha`. Preserve reservations across runs and policy changes, including uncertain API responses. Reconcile existing manual recovery attempts before invoking recovery; never bypass the controller to spend the budget again. An accepted receipt is not a CI pass.

Reruns require an external [investigation](evidence.md#ci-recovery-investigation) bound to the actual run ID, attempt and source SHA. Inspect failing jobs, test results and sanitized scan evidence first. `infrastructure` must identify the interruption and confirm no known test/scan failure; cancellation alone is insufficient. `artifacts-unavailable` applies only to otherwise successful CI when required hosted artifacts are missing/expired and no retained usable evidence exists; the command also checks live availability. Missing/duplicated required jobs or real test/scan failures remain held. API/auth failures are unavailable evidence, not proof that no run exists. Do not manufacture commits to trigger CI.

Recovery requires the candidate CI workflow to match the trusted target branch, with dispatch support committed on both the configured target branch and the selected branch; if unavailable, hold only the recovery request and continue ordinary reviews that can reuse valid existing CI. Never run uncommitted controller changes. The fallback runs in GitHub, not on the credentialed host. Focused sandbox tests for a repair or a specific uncovered behavior remain permitted when necessary; they do not replace required hosted CI.

Before publication, the controller rechecks CI for the exact reviewed source and, when the same successful run and attempt still match, returns `reportCiReuse` and a `[skip ci]` commit message ([report CI reuse](evidence.md#reports)). Do not dispatch or recover CI merely because that report-only head has no run. Pending source runs are waited on, failed runs investigated, and missing source evidence follows this recovery path.

## Repair, publication and merge

These continue the numbered [one PR at a time](controller-operations.md#one-pr-at-a-time) procedure after step 7.

8. Before a repair or replacement capture, run `checkpoint <evidence.json>` to retain the current review's crew and results in the trusted external stage journal. In automatic mode, route repairable blocking findings to [marc-crew-repair](../../marc-crew-repair/SKILL.md), respecting `policy.maxRepairCycles` cumulatively per PR. A repair agent receives only approved findings, permitted files, current commits, validation requirements and the remaining repair budget; it does not merge or approve its own work. Record the observed repair with `checkpoint <pre-repair-evidence.json> <repair-event.json>` using the [stage event contract](evidence.md#assessment-stages). Then collect a new capture, recompute specialist selection from the complete PR diff, route again and complete every required gate for the new route in new reviewer sessions; give them the repair diff and relevant prior findings as evidence to recheck, without carrying forward approval. A known application dependency repair requires full review without automatically requiring every technology specialist; unresolved/shared scope retains broad selection. If policy is deliberately switched back to report-only, record recommendations without applying them.
9. Run `report <evidence.json> <clean-PR-worktree>` from the trusted target branch. It sets `reportCreatedAt` once and writes exactly the report pair described under [report names](evidence.md#report-names-and-presentation); use the paths returned by the command. A same-minute collision stops without overwriting; inspect whether the assessment already exists before preparing a later report. Inspect for secrets/personal data and misleading claims. Use the returned `commitMessage` to commit just those two files with hooks disabled, then push without force to the verified existing producer branch. No `reportCiReuse` record means no skip marker: retain normal report-head CI. Reuse does not waive required source artifacts or scans. The instruction to run this workflow authorizes these report-only commits and pushes, not comments, unrelated changes or policy edits. Record timestamp, source head, report head, paths and outcomes in the external ledger. Do not amend prior reports or add a fake final merge result inside them.
10. After publication invoke the merge guard without requesting another build. With `reportCiReuse` it rechecks the exact report pair and the bound successful source run/attempt. If report-head CI exists, wait for it and require success; reuse cannot hide failures, incomplete jobs or API errors. Historical reports without the record still require report-head CI. Do not add another report commit merely to record CI. In report-only mode retain the same publication/evidence checks without merging. In automatic mode invoke `merge <external-evidence.json>`; the script rejects policy/report/source drift and uses a non-force merge-commit push. After success verify GitHub recognizes the PR as merged and inspect target-branch CI; record the actual result externally. Fetch and fast-forward the clean controller target branch before selecting the next PR, then recapture its new base. A failed/uncertain push requires reading remote refs and PR state before any retry. Stop the queue on unexpected merge state or failing post-merge target-branch CI.
