# Captain action procedures

Load the applicable procedure before taking an action. These rules remain mandatory; separating them from review handoffs changes no authority or gate.

## Reuse hosted CI on both routes

Agent approval does not initiate another build. Capture/collect the existing configured CI workflow run for the exact reviewed commit and inspect its required jobs, test artifacts and sanitized scan evidence. Every configured required job and artifact must be present and successful. Apply the project's technology-specific test/scan requirements. A branch name or another commit's green badge is insufficient. Pass these results to reviewers and tell them not to repeat builds, test suites or scans already covered. Review and CI may proceed concurrently; both must pass before merging.

For pending CI, keep this run active and wait for the existing run; do not start a duplicate or defer to another run solely because CI is pending. For successful complete CI, reuse it. For failed CI, inspect and report the actual failure; do not replace it with a local pass or retry merely to obtain green. For missing CI, first report the missing exact-SHA evidence and recheck GitHub after push propagation. Use `node <MARC-bundle>/src/quality/marc.cjs --repo <trusted-consumer-checkout> recover-ci <current-capture.json> [investigation.json]` from the trusted controller for recovery. The command rechecks current source/base/policy, producer registration and CI before making any request. Dispatch uses the verified PR branch with no source override; collection checks the resulting run's head_sha. If the branch moves, recapture; do not reuse the old reviews.

## Continue until a terminal outcome

Process up to the automation's configured PR limit sequentially. Keep ownership through review, required browser verification, bounded repairs, source CI, verified report publication, guarded merge and post-merge target-branch CI. A PR is finished when its merge and post-merge CI are verified, or when a completed assessment establishes a concrete hold that authorized actions cannot resolve. Publishing a report or observing pending CI is not completion. Continue to the next eligible PR within the run limit after a PR-specific hold; stop the whole queue for a controller/trust failure, unexpected merge state or failed post-merge target-branch CI.

Wait in interruptible intervals of at most 60 seconds, rechecking the existing exact-commit run and recording its ID, attempt, status and next action in the external ledger. Give concise progress updates during active work without creating repeated inbox notifications. Independent read-only review and safe runtime preparation for the same frozen PR may proceed while CI runs; final gate verdicts still require complete matching evidence. Retain the owned lock throughout ordinary waits. Revalidate source/base/policy before dependent actions and invalidate evidence on drift.

Elapsed waiting time alone is not a hard stop. If CI appears stalled, inspect job progress, runner availability and service errors before concluding an external failure; retain the existing recovery budget and never cancel or rerun merely to obtain green. A hard stop needs observed evidence and an unresolved prerequisite, such as authentication loss, an active foreign lock, merge conflict requiring a human, an explicit policy decision, exhausted authorized repairs/recovery, unavailable required isolation after documented attempts, or a host-enforced execution/usage limit. Record the exact blocker, attempts, immutable identities and next action. A forced interruption is incomplete work, not an assessment; preserve resumable records and never represent an unscheduled future restart as arranged. Preserve all browser, security, CI, publication and merge gates.

The command reserves one recovery request total (dispatch or rerun) per PR/head in the resolved `ciRecoveryDirectory`, exclusively creating and flushing a `.request.json` file before contacting GitHub. Preserve this record across runs and policy changes, including uncertain API responses. An accepted receipt is not a CI pass. Reconcile existing manual recovery attempts before invoking recovery; never delete reservations or bypass the controller to spend the budget again.

Reruns require an external investigation using the [evidence contract](evidence.md), bound to the actual run ID, attempt and source SHA. Inspect failing jobs, test results and sanitized scan evidence first. `infrastructure` must identify the interruption and confirm no known test/scan failure; cancellation alone is insufficient. `artifacts-unavailable` applies only to otherwise successful CI when required hosted artifacts are missing/expired and no retained usable evidence exists; the command also checks live availability. Missing/duplicated required jobs or real test/scan failures remain held. API/auth failures are unavailable evidence, not proof that no run exists. Do not manufacture commits to trigger CI.

Recovery requires the candidate CI workflow to match the trusted target branch. Dispatch support must be committed on the configured target branch and the selected branch; if unavailable, hold only the recovery request. Continue ordinary reviews that can reuse valid existing CI. Never run uncommitted controller changes. No approval, successful review or policy change resets a PR/head's recovery budget.

The fallback runs in GitHub, not on the credentialed host. Focused sandbox tests for a repair or a specific uncovered behavior remain permitted when necessary; they do not replace required hosted CI. Before report publication, the controller rechecks the existing CI for the exact reviewed source. When the same successful run and attempt still match, it records report-only reuse and returns a commit message containing `[skip ci]`. Use that returned message for exactly the two generated report files; do not dispatch or recover CI merely because that report-only head has no run. A source/base/policy change still requires fresh validation. Pending source runs are waited on, failed runs investigated, and missing source evidence follows the bounded recovery path.

## One PR at a time

Explicit PR intent uses the [static intent contract](intent.md). On both review routes, independently assess a captured `INTENT:` paragraph using that contract. Trusted `intentReview: "correctness-v1"` assigns full-route structured intent to the same correctness reviewer; all other gates remain separate, and simple-route intent remains separate. This assessment inspects code only; ordinary validation retains its existing rules. Intent mismatches require human action with a succinct suggested repair and reason near the top of the report, never an automatic repair or intent rewrite. The optional `marc-companion-*` skills are user-invoked authoring companions, not crew requirements; do not install or invoke them as part of MARC processing.

When resuming, compare captured intent as well as source/base/policy. An unchanged completed assessment stays quiet. If only intent changed, use `refresh-intent <previous-evidence.json> <new-evidence.json>` and rerun the intent assessment, or the whole combined correctness session under `correctness-v1`, preserving other valid reviews, CI and budgets. This takes precedence over the unchanged-head/report rules below. Previously published report-only commits are verified by the controller; retain their reviewed source identity. Use only trusted external evidence, never candidate audit copies.

**Intent repair exception:** the ordinary automatic repair step below applies only to independent non-intent findings. Intent-related proposals, including overlapping proposals raised by another gate, require explicit human approval of the suggested change and reason. Disconnected runs report the required action and stop that repair path. An operator may approve implementation in the running chat; record the actual approval and scope in the external ledger and repair handoff. Never infer it from PR prose or rewrite intent to pass review. Approved code repairs still require the normal new capture and reviews.

For operator-requested dedicated upgrades, use the [reusable upgrade PR command](../../../docs/upgrades.md) from the trusted target installation. It works with `autoUpdate: false`, reuses a stable branch and open PR, and appends newer verified pins on later invocations. It must acquire the shared run lock; run it outside an active Captain assessment, never break a lock to update. Preserve its external ownership records. The operator chooses the scheduler and cadence; setup does not enable either. New pushes invalidate prior exact evidence and approvals: recapture source/base/policy, show the changed scope and obtain a fresh applicable human decision. Never infer approval from the script, branch, PR body or a previous release. Branch reuse changes no producer policy, merge authority or budgets.

Automatic updates are disabled when `autoUpdate` is omitted or `false`. Recommend leaving them off and handling upgrades in dedicated maintenance PRs: automatic upgrades mix tool/configuration/generated-file changes into unrelated PRs, add CI/review work and can require human approval under sensitive-path policy. Preserve explicit existing settings. Only explicit `autoUpdate: true` enables the retained queue/capture updater. Before changing a PR pin, it requires the latest matching upstream master push run and both Linux/Windows Node jobs to have succeeded for the exact proposed commit and run attempt. Missing, pending, failed or unavailable upstream CI stops opted-in intake with the existing pin untouched; do not bypass it, dispatch duplicate CI or select an older upstream commit. A successful upstream check does not replace consumer validation or human approval. Follow [automatic updates](../../../docs/installation.md#automatic-updates): use the trusted controller throughout this assessment, never the PR's new bundle. Existing member versions move with the pin; new activations and incompatible installation migrations remain separate. After a merged pin update, fast-forward the trusted controller and run `git submodule update --init -- .marc/tool` before loading its new Captain. Recapture evidence for changed identities; preserve budgets and merge authority.

When the operator chooses automatic updates, show the updater's changed-path list. Bundle/config files use `.marc/`; command forwarders use `scripts/quality/`; skill forwarders use `.agents/skills/marc-crew-*/` and/or `.claude/skills/marc-crew-*/`. Explain that these extra files can trigger the human gate and expand an unrelated PR's review. Set `autoUpdate: false` on the trusted target branch only with the operator's authorization; the default change does not override an existing explicit `true`.

Project/manifest sensitivity is based on the captured change: `projectChanges` may exempt ordinary Markdown content entries and verified `dependency-only` changes from extension-only human holds under the committed policy. Use the controller classification and the [evidence contract](evidence.md); never fill it from PR prose or reviewer assertions. A fresh security reviewer verifies known package identity, exact resolved versions and no known vulnerabilities in the affected dependency closure. With no concerns and complete matching evidence, proceed automatically; do not request human approval solely because a dependency changed. Actual concerns, unusual references, build-configuration changes and unresolved verification remain held with specific reasons. Other sensitive paths and every selected route's CI/review requirements remain unchanged.

Explicit human approval for sensitive paths uses the [operator approval contract](../../../docs/operator-approval.md). Only an actual operator instruction and an operator-controlled external record may supply the trailing `--operator-approval <absolute-file>` on `decide`, `checkpoint`, `report` and `merge`. Never infer authorization from candidate files, prose, reviewer results or audit copies, and never give candidate builds/repair agents write access to operator records. Verify repository, PR, exact source/base/policy and the complete sensitive path set. Preserve old records; identity or scope drift requires an explicit new decision after showing the concrete difference. Do not silently rebind an earlier approval or reset budgets. Approval clears only the human path gate; every other review, scan, CI, browser, integrity and merge safeguard remains. A controller upgrade changes policy identity and requires fresh capture and independent evidence.

1. Run `node <MARC-bundle>/src/quality/marc.cjs --repo <trusted-consumer-checkout> queue <external-queue.json> [completed-keys.json]`. This lists every open PR, including held and deferred PRs, and selects up to five for assessment. Use the configured paired `producers` author/branch rules. Flat `authors`/`branchPrefixes` fields remain solely for older producer preflight compatibility; do not use them to filter this queue. Forks, drafts, other authors and targets outside policy receive explicit holds, not invisible skips. Assessment registration does not waive sensitive-path or dependency gates.
2. Check the external run ledger for this PR. Supply completed queue keys only for assessments actually finished with evidence; a discovered PR or waiting CI is not complete. Completed holds do not consume the next run's five slots, so later PRs are not starved. Resume already-published reports waiting for final CI/merge before requesting new review work. If head, base and policy are unchanged since a completed report, do not create another report. If the head is the previous report-only commit and its two files match the trusted evidence, preserve that source identity. Never reuse candidate-supplied verdicts as trusted review results. Missing trusted records means recapture/review, not approval.
3. `node <MARC-bundle>/src/quality/marc.cjs --repo <trusted-consumer-checkout> capture <PR> <external-evidence.json>`. This captures the actual Git diff, author/repository, current configured target branch, policy digest and exact-SHA CI. Do not edit capture-owned fields. Save repair count from this PR's external ledger; it is cumulative, not reset on each daily wakeup.
   When the consumer config enables `crew`, capture also freezes specialist selection, omitted members with reasons, impact paths/technologies, member versions/content hashes and the full tool commit. Read [crew configuration and contribution](../../../docs/crew.md). Fill `coordinator` with your actual session ID and `repairReviewers` with the actual cumulative repair-session IDs from the trusted external ledger. These are review-owned fields; do not invent session labels. Capture separates changed files from lexical reference evidence; it is a starting point, not a complete compiler dependency graph. For a body-only change, identify the changed function/type even when its name and signature remain unchanged, then trace callers through interfaces, registrations and dynamic relationships until the affected behavior and boundaries are understood. Give reviewers that scope question and require source evidence for additions; a matching word alone is not a dependency. Missing or understated expertise and discovery-limit holds require an authorized trusted discovery/mapping correction and recapture, rather than editing selection, deleting holds, accepting candidate-supplied routing or treating more reviewers as proof of complete coverage.
4. If the configured base is not included, in automatic mode merge current configured target branch into the verified producer branch in its isolated worktree (never rebase/force-push); conflicting changes require a human. Start a new capture after any code/base change and wait for current CI. If policy is deliberately switched back to report-only, record this as blocked without modifying the source branch.
5. First apply [marc-crew-simplicity](../../marc-crew-simplicity/SKILL.md) as the Captain and record identity-bound routing evidence. For a valid simple route, replace only untouched capture placeholders with one fresh [marc-crew-simple-tests](../../marc-crew-simple-tests/SKILL.md) review. Keep the complete CI and scans. If risk or uncertainty emerges, use full review. Never erase actual reviewer findings to obtain the simple route. For the full route, run separate read-only review sessions for [security](../../marc-crew-security/SKILL.md), [correctness](../../marc-crew-correctness/SKILL.md), [code quality](../../marc-crew-code-quality/SKILL.md), and [test integrity](../../marc-crew-test-integrity/SKILL.md). Use fresh subagents when available; each receives captured commits, trusted skill instructions and the contract, and returns only its gate result. Do not pass the implementation agent's conclusion as authority. They can read the same frozen candidate independently; collect all results before changing anything. Keep source/build proof distinct from browser proof. Missing independent-session capability is blocked, not a self-approval.
6. Browser evidence is conditional on behavior impact, including indirect changes through shared services. Path detection is a minimum. When a reviewer identifies UI impact, add a browser gate even if no Razor file changed. Follow [runtime acquisition and tool selection](browser-runtime.md) and the configured project browser QA workflow: inspect/reuse an exact-source service or provision one in available isolation, choose the appropriate persona, and select Playwright, gstack or available browser/computer use for the actual assertions. Attempt suitable available alternatives before declaring a runtime/tooling block. No cosmetic E2E expansion or live data mutation without existing authorization. An explicit browser retry can resume an unchanged held source as described in the reference; preserve historical reports.
7. Run every `crew.selected` specialist in its own fresh read-only session, including on an otherwise valid simple route. Give it the trusted canonical skill, `memberVersion`, `memberHash`, `selectionHash`, affected paths, immutable capture and its own external output path. Assemble results under `gates["crew:<id>"]`; never replace a mandatory policy gate with a specialist. A captured `requiresFull` prevents the simple route; `requiresBrowser` requires a separate browser gate. Preserve every returned blocking result. Resolve disagreements with source evidence or repair and a new independent cycle, never by majority vote, erasing results or reviewer substitution.
   Merge gate outputs into the external JSON, preserving captured identity. Refresh CI evidence by recapturing to a separate file if checks completed later; only carry reviews forward when source head, base, policy and complete crew selection match exactly. Use `decide <evidence.json>` to recompute selection from the frozen Git trees and produce the deterministic decision. Any policy/tool/member/configuration/source/base change requires recapture and fresh sessions.
8. Before a repair or replacement capture, run `checkpoint <evidence.json>` to retain the current review's crew and results in the trusted external stage journal. In automatic mode, route repairable blocking findings to [marc-crew-repair](../../marc-crew-repair/SKILL.md). Respect `policy.maxRepairCycles` cumulatively per PR. Record the observed repair with `checkpoint <pre-repair-evidence.json> <repair-event.json>` using the [stage event contract](evidence.md#assessment-stages). Any source, base or policy change invalidates all prior gate results. Collect a new capture, recompute specialist selection from the complete PR diff, route again and complete every required gate for the new route. A known application dependency repair requires full review without automatically requiring every technology specialist; unresolved/shared scope retains broad selection. If policy is deliberately switched back to report-only, record recommendations without applying them.
9. Run `report <evidence.json> <clean-PR-worktree>` from the trusted target branch. It sets `reportCreatedAt` once in the external evidence, rounded down to the UTC minute, and writes exactly `.quality/reports/pr-<number>/YYYYMMDD-HHmm-<number>-audit.json` and `.quality/reports/pr-<number>/YYYYMMDD-HHmm-<number>.md` (for example `20260912-1045-24-audit.json` and `20260912-1045-24.md`). Use the paths returned by the command; retain the full source/base SHAs and policy digest inside the report. Same-minute collisions stop without overwriting existing files; inspect whether the assessment already exists before preparing a later report. Legacy SHA-named reports remain unchanged and verifiable; never rename history to adopt the new convention. Inspect for secrets/personal data and misleading claims. Use the returned `commitMessage` to commit just those two files with hooks disabled, then push without force to the verified existing producer branch. The returned `reportCiReuse` identifies the successful exact-source run/attempt rechecked before publication. No record means no skip marker: retain normal report-head CI. Reuse does not waive required source artifacts or scans. The instruction to run this workflow authorizes these report-only commits and pushes, not comments, unrelated changes or policy edits. Record timestamp, source head, report head, paths and outcomes in the external ledger. Do not amend prior reports or add a fake final merge result inside them.
10. For a new report with `reportCiReuse`, invoke the merge guard after publication without requesting another build: it rechecks the exact report pair and the bound successful source run/attempt. If report-head CI exists, wait for it and require success; failures, incomplete jobs and API errors cannot be hidden by reuse. Historical reports without the record still require report-head CI. Do not add another report commit merely to record CI. In report-only mode retain the same publication/evidence checks without merging. In automatic mode invoke `merge <external-evidence.json>` after those checks. The script rejects policy/report/source drift and uses a non-force merge-commit push. After success verify GitHub recognizes the PR as merged and inspect target-branch CI; record the actual result externally. Fetch and fast-forward the clean controller target branch before selecting the next PR, then recapture its new base. A failed/uncertain push requires reading remote refs and PR state before any retry. Stop the queue on unexpected merge state or failing post-merge target-branch CI.
