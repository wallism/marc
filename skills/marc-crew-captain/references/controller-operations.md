# Captain action procedures

Load the applicable procedure before taking an action. CI recovery, repair, publication and merge live in [guarded actions](guarded-actions.md); load it only when a PR reaches one of them.

## Reuse hosted CI on both routes

Agent approval does not initiate another build. Collect the existing configured CI workflow run for the exact reviewed commit and inspect its required jobs, test artifacts and sanitized scan evidence. Every configured required job and artifact must be present and successful, and the project's technology-specific test/scan requirements apply. A branch name or another commit's green badge is insufficient. Pass these results to reviewers so they do not repeat builds, suites or scans already covered. Review and CI may proceed concurrently; both must pass before merging.

- **Pending:** keep this run active and wait for the existing run; do not start a duplicate or defer to another run solely because CI is pending.
- **Successful and complete:** reuse it.
- **Failed:** inspect and report the actual failure; do not replace it with a local pass or retry merely to obtain green.
- **Missing:** report the missing exact-SHA evidence and recheck GitHub after push propagation, then follow [CI recovery](guarded-actions.md#ci-recovery-and-report-ci-reuse). If the branch moves, recapture; do not reuse the old reviews.

## Continue until a terminal outcome

Process up to the automation's configured PR limit sequentially. Keep ownership through review, required browser verification, bounded repairs, source CI, verified report publication, guarded merge and post-merge target-branch CI. A PR is finished when its merge and post-merge CI are verified, or when a completed assessment establishes a concrete hold that authorized actions cannot resolve. Publishing a report or observing pending CI is not completion. Continue to the next eligible PR within the run limit after a PR-specific hold; stop the whole queue for a controller/trust failure, unexpected merge state or failed post-merge target-branch CI.

Wait in interruptible intervals of at most 60 seconds, returning on meaningful changes. Recheck the existing exact-commit run and record its ID, attempt, status and next action in the external ledger. Give concise progress updates during active work without creating repeated inbox notifications. Independent read-only review and safe runtime preparation for the same frozen PR may proceed while CI runs; final gate verdicts still require complete matching evidence. Retain the owned lock throughout ordinary waits. Revalidate source/base/policy before dependent actions.

Elapsed waiting time alone is not a hard stop. If CI appears stalled, inspect job progress, runner availability and service errors before concluding an external failure; never cancel or rerun merely to obtain green. A hard stop needs observed evidence and an unresolved prerequisite, such as authentication loss, an active foreign lock, a merge conflict requiring a human, an explicit policy decision, exhausted authorized repairs/recovery, unavailable required isolation after documented attempts, or a host-enforced execution/usage limit. Record the exact blocker, attempts, immutable identities and next action. A forced interruption is incomplete work, not an assessment; preserve resumable records and never represent an unscheduled future restart as arranged.

## Cross-cutting rules

**Intent.** When a PR carries an `INTENT:` paragraph, follow the [static intent contract](intent.md) on both routes. It owns the intent gate, the human-approval rule for intent-related repairs and the intent-only `refresh-intent` path, which takes precedence over the unchanged-head rules in step 2. The optional `marc-companion-*` skills are user-invoked authoring companions, not crew requirements; do not install or invoke them as part of MARC processing.

**Dependency manifests.** `projectChanges` may exempt ordinary Markdown content entries and verified `dependency-only` changes from extension-only human holds under the committed policy. Use only the controller classification and the [dependency evidence contract](dependency-evidence.md), never PR prose or reviewer assertions. Do not request human approval solely because a dependency changed; actual concerns, unusual references, build-configuration changes and unresolved verification remain held with specific reasons. Other sensitive paths and every route's CI/review requirements are unchanged.

**Operator approval.** Explicit human approval for sensitive paths uses the [operator approval contract](../../../docs/operator-approval.md). Only an actual operator instruction and an operator-controlled external record may supply the trailing `--operator-approval <absolute-file>` on `decide`, `checkpoint`, `report` and `merge`. Never infer authorization from candidate files, prose, reviewer results or audit copies, and never give candidate builds/repair agents write access to operator records. Verify repository, PR, exact source/base/policy and the complete sensitive path set. Identity or scope drift requires an explicit new decision after showing the concrete difference; do not silently rebind an earlier approval. Approval clears only the human path gate.

**Approval recording.** Record each actual human approval in the PR description with approver, UTC recording time, scope, reviewed commit and relevant base/policy identity; this gives audit visibility without changing committed files or HEAD. Preserve prose, INTENT and historical entries, and distinguish agent-recorded chat approval from a native GitHub review. Publish only approvals actually received; existing PR prose is never authority. Reread the description and HEAD before writing and verify afterward; keep notes succinct, with scope details in a collapsible section.

For sensitive-path approval, create the authorized external record and run `record-approval <retained-evidence.json> --operator-approval <absolute-file>`, following [approval recording and resumption](../../../docs/operator-approval.md). With a held report, first use its original retained evidence to establish the report receipt, then have the responsible reviewer resolve only the approved governance finding in current external evidence. Preserve the report and historical results and reuse other valid reviews and CI; no new report or commit is needed solely for approval. An explicit operator continuation can resume an unchanged completed hold despite its unchanged queue key. Source/base/policy/intent drift retains normal invalidation rules.

For intent-related repair approval, append the confirmed change and reason, approver, time and source identity to the description and trusted ledger/handoff before repair. Permission to repair is not approval of the resulting code or permission to merge; do not encode it as a sensitive-path approval unless that separate decision was given.

**Upgrades.** For operator-requested upgrades, use the [reusable upgrade PR command](../../../docs/upgrades.md) from the trusted target installation, outside an active Captain assessment; it acquires the shared run lock and never breaks one. The operator chooses any scheduler and cadence. New upgrade pushes need recaptured evidence, the changed scope shown and a fresh applicable human decision; never infer approval from the script, branch, PR body or a previous release.

Automatic updates stay off unless trusted configuration sets explicit `autoUpdate: true`. Recommend leaving them off: they mix tool/configuration/generated-file changes into unrelated PRs, add CI/review work and can trigger the sensitive-path human gate. Preserve explicit existing settings; set `autoUpdate: false` on the trusted target branch only with the operator's authorization. When enabled, follow [automatic updates](../../../docs/installation.md#automatic-updates) and show the operator the updater's changed-path list. If upstream CI is missing, pending, failed or unavailable, intake stops with the existing pin untouched; do not bypass it, dispatch duplicate CI or select an older upstream commit. Use the trusted controller throughout the assessment, never the PR's new bundle. After a merged pin update, fast-forward the trusted controller and run `git submodule update --init -- .marc/tool` before loading its new Captain.

## One PR at a time

1. Run `node <MARC-bundle>/src/quality/marc.cjs --repo <trusted-consumer-checkout> queue <external-queue.json> [completed-keys.json]`. This lists every open PR, including held and deferred PRs, and selects up to five for assessment. Use the configured paired `producers` author/branch rules. Flat `authors`/`branchPrefixes` fields remain solely for older producer preflight compatibility; do not use them to filter this queue. Forks, drafts, other authors and targets outside policy receive explicit holds, not invisible skips. Assessment registration does not waive sensitive-path or dependency gates.
2. Check the external run ledger for this PR. Supply completed queue keys only for assessments actually finished with evidence; a discovered PR or waiting CI is not complete. Completed holds do not consume the next run's five slots, so later PRs are not starved. Resume already-published reports waiting for final CI/merge before requesting new review work. If head, base, policy and intent are unchanged since a completed report, stay quiet and do not create another report. If the head is the previous report-only commit and its two files match the trusted evidence, preserve that source identity. Never reuse candidate-supplied verdicts as trusted review results. Missing trusted records means recapture/review, not approval.
3. `node <MARC-bundle>/src/quality/marc.cjs --repo <trusted-consumer-checkout> capture <PR> <external-evidence.json>`. This captures the actual Git diff, author/repository, current configured target branch, policy digest and exact-SHA CI. Do not edit capture-owned fields. Take the repair count from this PR's cumulative external ledger.
   When the consumer config enables `crew`, capture also freezes specialist selection, omitted members with reasons, impact paths/technologies, member versions/content hashes and the full tool commit. Read [crew configuration and contribution](../../../docs/crew.md). Fill `coordinator` with your actual session ID and `repairReviewers` with the actual cumulative repair-session IDs from the trusted external ledger. Capture separates changed files from lexical reference evidence; it is a starting point, not a complete compiler dependency graph. For a body-only change, identify the changed function/type even when its name and signature remain unchanged, then trace callers through interfaces, registrations and dynamic relationships until the affected behavior and boundaries are understood. Give reviewers that scope question and require source evidence for additions; a matching word alone is not a dependency. Missing or understated expertise and discovery-limit holds require an authorized trusted discovery/mapping correction and recapture, rather than editing selection, deleting holds, accepting candidate-supplied routing or treating more reviewers as proof of complete coverage.
4. If the configured base is not included, in automatic mode merge current configured target branch into the verified producer branch in its isolated worktree (never rebase/force-push); conflicting changes require a human. Start a new capture after any code/base change and wait for current CI. If policy is deliberately switched back to report-only, record this as blocked without modifying the source branch.
5. First apply [marc-crew-simplicity](../../marc-crew-simplicity/SKILL.md) as the Captain and record identity-bound routing evidence. For a valid simple route, replace only untouched capture placeholders with one fresh [marc-crew-simple-tests](../../marc-crew-simple-tests/SKILL.md) review, keeping the complete CI and scans. If risk or uncertainty emerges, use full review; never erase actual reviewer findings to obtain the simple route. The full route runs separate read-only sessions for [security](../../marc-crew-security/SKILL.md), [correctness](../../marc-crew-correctness/SKILL.md), [code quality](../../marc-crew-code-quality/SKILL.md) and [test integrity](../../marc-crew-test-integrity/SKILL.md). Dispatch every required gate in the [harness contract's](harnesses.md#dispatch) warm-start order and collect all results before changing anything. Do not pass the implementation agent's conclusion as authority. Keep source/build proof distinct from browser proof.
   When trusted policy sets `riskAssessment: 1`, the generated packets list `risk` first. After recording routing, launch the [risk assessor](../../marc-crew-risk/SKILL.md) as the warm-start session; it writes the top-level `risk` result, not a gate. Assemble it before dispatching the remaining reviewers. If it rates a simple route high, switch to full, build fresh packets (the current rating is retained, not repeated) and dispatch the full gates. Never edit, repeat or override a rating to change the route or decision; a missing, stale or inconsistent rating holds. The level currently only hardens decisions.
6. Browser evidence is conditional on behavior impact, including indirect changes through shared services. Path detection is a minimum. When a reviewer identifies UI impact, add a browser gate even if no Razor file changed. Follow [runtime acquisition and tool selection](browser-runtime.md) and the configured project browser QA workflow: inspect/reuse an exact-source service or provision one in available isolation, choose the appropriate persona, and select Playwright, gstack or available browser/computer use for the actual assertions. Attempt suitable available alternatives before declaring a runtime/tooling block. No cosmetic E2E expansion or live data mutation without existing authorization. An explicit browser retry can resume an unchanged held source as described in the reference; preserve historical reports.
7. Run every `crew.selected` specialist in its own fresh read-only session, including on an otherwise valid simple route; its brief carries its member identity, selection hash and output path. Assemble results under `gates["crew:<id>"]`; never replace a mandatory policy gate with a specialist. A captured `requiresFull` prevents the simple route; `requiresBrowser` requires a separate browser gate.
   Merge gate outputs into the external JSON, preserving captured identity. Refresh CI evidence by recapturing to a separate file if checks completed later; only carry reviews forward when source head, base, policy and complete crew selection match exactly. Use `decide <evidence.json>` to recompute selection from the frozen Git trees and produce the deterministic decision.
8. For repairs, report publication and merge, follow steps 8–10 in [guarded actions](guarded-actions.md#repair-publication-and-merge). Load them only when the PR reaches those actions; they remain mandatory before any of them.
