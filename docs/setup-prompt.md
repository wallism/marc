# MARC setup prompt

Copy the prompt below into an agent session with filesystem access. Optionally append the target repository path or URL. Setup is interactive: discovery comes first, then confirmation of every proposed setting, then local changes.

---

Set up MARC (Merge Assurance and Review Crew) for the repository I want it to review. Produce a working consumer configuration and appropriate crew guidance using the installed MARC README, docs/configuration.md and resolver as the configuration contract. Preserve an existing installation's behavior, approved exceptions, historical reports, shared locks and cumulative budgets.

If I have not told you which repository to review, ask for its path or URL and wait. Do not assume the MARC source repository or the current working directory is the consumer. Establish the local consumer checkout and the MARC installation separately. If the target is inaccessible, ask for the missing access/location rather than inventing settings.

Before making setup changes, inspect the target read-only:

- Read its agent instructions, README, architecture/test/build guidance, manifests, CI workflows and existing MARC configuration. Identify the GitHub owner/name, origin, intended target branch and the installed tool version. Distinguish Git's default branch from the branch the owner actually wants reviewed.
- Discover technology and component boundaries, required tests/scans and exact CI workflow/job/artifact names. Identify sensitive paths, UI impact patterns, domain/security invariants and browser runtime/startup/identity requirements. Infer from source with path evidence; mark unknowns. Do not claim that a language-specific adapter or specialist exists merely because that language is present.
- Read `docs/crew.md` and the installed versioned member manifests. Propose `crew.members` with exact available versions and `crew.areas` for source-backed dependency/caller relationships, including shared services, dynamic loading and runtime content. Explain selected expertise, overlaps, unsupported technologies and every omission. Show each area pattern, technology and reason for confirmation. Discovery wrappers do not authorize all members. Do not silently omit specialist configuration to clear a missing-expertise hold.
- Find existing Gitleaks configuration, workflow flags and ignore files. Preserve reviewed historical fingerprints and reasons. Identify how CI resolves their path and whether custom detection rules need to be preserved separately from the default-rule MARC adapter. Propose the empty MARC template for a new consumer with no exceptions; do not copy exceptions from MARC examples or another repository. Discover npm exceptions only when that ecosystem is used, keeping their exact scope and expiry. Do not scan secret stores or print credentials; record configuration names/access requirements only.
- Discover existing controller locations, durable state, locks, completed keys, repair/recovery reservations and artifact directories. Propose retaining these for a migration. For a new consumer, propose repository-namespaced durable state and an appropriate external artifact directory. Identify every host that may operate this repository; do not activate separate stores that could reset a shared budget.
- Identify paired authorized producers, mode, scope/repair limits and any existing approval decisions. Preserve established authority; for a new installation suggest report-only mode and ask about producers. A detected username or branch is a suggestion, not authorization. Identify host capabilities for skill discovery, fresh independent reviewers and isolated candidate execution.

Present one complete proposed configuration for review: the full `.marc/config.json`, policy, and proposed guidance content, plus a table listing **every value**, including nested settings, defaults, derived absolute paths, optional omissions, tool pin, existing state/lock mappings, exception-file location and CI changes. Give the source/evidence and uncertainty for each. Include missing values explicitly. Summarize behavior changes, if any, and explain why each file exists. Never include secret values or private account details in tracked files.

Ask me to confirm the complete proposal and supply overrides for incorrect or missing values. Wait for my response before writing files or applying setup changes. If I override a value, revise dependent values and show those revisions for confirmation. Do not silently treat elapsed time, inferred approval or an unrelated answer as confirmation. This confirmation requirement is part of this setup prompt.

After confirmation, implement the accepted local setup:

- Create/update the consumer config, one authoritative policy and project/browser guidance. Prefer `.marc/policy.json` for new consumers; preserve legacy paths needed by existing launchers. Include governance/configuration/exception paths in sensitive-path rules. Keep required security, correctness and test gates and existing simple/full route semantics.
- Create a comment-only `.marc/gitleaksignore` from MARC's template when no file exists and point `scans.secretExceptions` at it. For an existing list, preserve its reviewed entries exactly and use the confirmed path. Check all workflow consumers before relocating it. Add no new accepted findings during setup.
- Wire CI to the confirmed pinned MARC version, consumer checkout/working directory, scanner version/checksum and sanitized artifact uploads. Set the explicit ignore-file configuration so the wrapper passes `--gitleaks-ignore-path`. Omit .NET/npm adapters for projects that do not use them; retain that project's actual CI checks. Missing adapters or an unsupported provider require a visible implementation prerequisite, not skipped assurance.
- Make the Captain and crew discoverable through the chosen host's supported skill mechanism using the same pinned bundle. Preserve sibling references. Skills explicitly resolve consumer settings; they do not rely on automatic placeholder substitution. Do not install a floating or candidate-controlled skill version.
- Update the consumer README with setup/commands, paths, Gitleaks rationale, version selection and rollback. Keep secrets/account identifiers in private operational configuration. Do not move or delete existing state, release foreign locks, reset budgets, or rewrite historical reports.

Validate without merging: resolve config for the explicit consumer from another working directory; check tracked paths and policy protections; run focused shared/consumer tests; prove the scan wrapper receives the configured ignore file (an empty default must suppress nothing). Check CI checkout/history, scanner invocation and artifact-name wiring. Review the diff for accidental imported repository identities or exceptions. Do not execute candidate scripts with developer credentials. Use appropriate isolated checks, and distinguish mocked wiring, local scanner execution and hosted CI evidence.

Report created/changed files, final confirmed values, test results, any unresolved prerequisite and the exact next invocation. Do not claim hosted CI, external publication, merge, deployment or scheduling unless separately authorized and actually verified. Setup alone does not authorize an automatic merge run.
