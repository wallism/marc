# MARC setup prompt

Copy the prompt below into an agent session with filesystem access. Optionally append the target repository path or URL. First setup confirms every proposed setting, including the recommended `autoUpdate: false`. Reruns preserve explicit settings and add missing discovery files; configuration changes, manual upgrades and installation migrations need authorization.

---

Set up MARC (Merge Assurance and Review Crew) for the repository I want it to review. Produce a working consumer configuration and appropriate crew guidance using the installed MARC README, docs/configuration.md and resolver as the configuration contract. Preserve an existing installation's behavior, approved exceptions, historical reports, shared locks and cumulative budgets.

Omit `agents` model/reasoning overrides unless I request them; preserve any existing overrides on reruns. Briefly point to the optional JSON example in `docs/configuration.md`. Models and reasoning levels must be available in the chosen harness.

If I have not told you which repository to review, ask for its path or URL and wait. Do not assume the MARC source repository or the current working directory is the consumer. Establish the local consumer checkout and the MARC installation separately. If the target is inaccessible, ask for the missing access/location rather than inventing settings.

Before making setup changes, inspect the target read-only:

When explaining ongoing upgrades, point to `docs/upgrades.md`: the explicit upgrade command reuses one stable branch and open PR and can run from the developer's existing scheduler with `autoUpdate: false`. Explain persistent shared state, verified upstream CI and fresh human approval when identities change. Do not create a schedule, run the publishing command or change producer policy as part of setup without authorization.

On reruns, treat existing configuration, exact member versions, areas, policy, guidance, CI and host customizations as authoritative. Do not regenerate them from defaults, reformat unchanged files or repeat answered questions. Preview the current pinned installer, then add missing command/crew forwarding files without asking again; preserve and report differing existing files. Installing discovery files does not activate specialist gates: propose missing source-backed `crew.members` and area additions for confirmation. If nothing needs adding or upgrading, report that setup is already current and make no writes.

Check for updates read-only using an available reviewed upstream commit in a separate checkout; do not move the consumer submodule during discovery. Compare each existing member's installed and available manifest versions, skill content and references; summarize changes using the improvement register and actual diff. Flag changed content at the same version as unversioned drift. Core skills without manifest versions use bundle commits and content diffs. If upstream cannot be checked, report update availability as unknown. A missing forwarding file is not a version upgrade.

Explain that `autoUpdate` defaults to `false`, including when omitted, and recommend leaving it off. Show `autoUpdate: false` explicitly in the first-install proposal. Enabling it adds pin/config/generated-file changes to ordinary PRs, complicates their review, requires fresh CI/evidence and can hold them for human approval under sensitive-path policy. Prefer a dedicated upgrade PR through the operator's existing maintenance workflow. Preserve an existing explicit `true` or `false` on reruns; propose disabling `true` with the reason rather than silently changing it. Previously omitted settings now resolve to false; disclose this behavior change. If the operator explicitly opts in, explain upstream CI verification, PR mutation and trusted-controller adoption after merge from `docs/installation.md#automatic-updates`. Opt-in authorizes the update mechanism, not sensitive-path merge approval. Setup alone does not start PR processing. Apply a manual upgrade only when authorized, showing the full SHA, affected members and behavior changes. New-member activations and forwarding-contract migrations still require confirmation. Preserve customizations; do not use `--replace-existing` on an ordinary rerun.

Follow `docs/technology-discovery.md` for the discovery exclusion list, evidence-based language/framework identification, recommended member output and pending-PR handoff. Inventory tracked source, infrastructure, build and runtime files independently of existing technology lists and router mappings. Apply the documented exclusions before research; document consumer overrides without inventing configuration keys. Exclusions skip language identification and specialist creation only, never changed-file reporting, security checks or policy gates. Confirm extensions with contents, manifests, imports and CI/build commands; consult primary documentation for unresolved unfamiliar formats and reuse the result. Identify missing router detection/area mappings separately from missing expertise.

For a React web consumer, use manifests and imports/callers to confirm React and its framework/version. Consult docs/crew.md for `react@1.0.0`, JavaScript/front-end companion members and explicit `react`/`web` areas covering components and Hooks, including `.js`/`.ts`. JSX alone is not React proof. Present all proposed areas and members for confirmation; do not opt non-React consumers into React. Confirm isolated browser runtime availability: a specialist is not a runtime provisioning adapter.

- Read its agent instructions, README, architecture/test/build guidance, manifests, CI workflows and existing MARC configuration. Identify the GitHub owner/name, origin, intended target branch and the installed tool version. Distinguish Git's default branch from the branch the owner actually wants reviewed.
- Discover technology and component boundaries, required tests/scans and exact CI workflow/job/artifact names. Identify sensitive paths, UI impact patterns, domain/security invariants and browser runtime/startup/identity requirements. Infer from source with path evidence; mark unknowns. Do not claim that a language-specific adapter or specialist exists merely because that language is present.
- Read `docs/crew.md` and the installed versioned member manifests. Propose `crew.members` with exact available versions and `crew.areas` for source-backed dependency/caller relationships, including shared services, dynamic loading and runtime content. Explain selected expertise, overlaps, unsupported technologies and every omission. Show each area pattern, technology and reason for confirmation. Discovery wrappers do not authorize all members. Do not silently omit specialist configuration to clear a missing-expertise hold.
- For each expertise gap, distinguish an available member that needs activation or a bundle upgrade from missing specialist coverage. When coverage is missing, propose using `skills/marc-crew-creator/SKILL.md` to create a member (or extend an existing member where appropriate) and contribute the change through a PR back to the MARC source repository. Include the source-backed technology/framework scope, companion members, exclusions, required research and validation, and any separate scanner/runtime prerequisites. For example, confirmed React web code without an available React specialist should produce a React-member creation proposal. Include this authoring/contribution proposal in setup confirmation; do not invent an available member version or add a nonexistent member as working configuration. If the installed bundle lacks the creator skill, identify access to a reviewed version as a prerequisite.
- Find existing Gitleaks configuration, workflow flags and ignore files. Preserve reviewed historical fingerprints and reasons. Identify how CI resolves their path and whether custom detection rules need to be preserved separately from the default-rule MARC adapter. Propose the empty MARC template for a new consumer with no exceptions; do not copy exceptions from MARC examples or another repository. Discover npm exceptions only when that ecosystem is used, keeping their exact scope and expiry. Do not scan secret stores or print credentials; record configuration names/access requirements only.
- Discover existing controller locations, durable state, locks, completed keys, repair/recovery reservations and artifact directories. Propose retaining these for a migration. For a new consumer, propose repository-namespaced durable state and an appropriate external artifact directory. Identify every host that may operate this repository; do not activate separate stores that could reset a shared budget.
- Identify paired authorized producers, mode, scope/repair limits and any existing approval decisions. Preserve established authority; for a new installation suggest report-only mode and ask about producers. A detected username or branch is a suggestion, not authorization. Identify host capabilities for skill discovery, fresh independent reviewers and isolated candidate execution.

Identify all intended harnesses (Codex, Claude Code and/or Cursor), preserving the selection documented by an existing consumer. Use the [harness contract](../skills/marc-crew-captain/references/harnesses.md) to inspect discovery, effective project/user instructions, reviewer-session identity and fresh-context capabilities. Do not infer operating capability from a discovered skill alone. Propose one shared bundle, policy, state directory and lock across harnesses. Record the exact installer `--hosts` selection in the consumer README; pass it on both preview and application, including upgrades. Codex remains the default when no host option is supplied. Claude Code uses `.claude/skills`; Codex and Cursor share `.agents/skills`. Report conflicting same-name wrappers without replacing customizations or relying on discovery precedence. Do not create permissive tool settings, hooks, schedules or a second controller merely to support another harness.

Inspect sensitive-path protection for nested and root `.agents/`, `.claude/`, `.cursor/`, `.codex/`, `AGENTS.md`, `CLAUDE.md` and `.cursorrules`. Propose missing coverage as a policy change under the existing confirmation process. Tracked harness inputs are included in the controller's policy digest; effective global/untracked inputs require separate inspection and cannot be described as digest-bound. Conflicting instructions or unavailable independent reviewers are an operating prerequisite, not grounds to weaken the review gates.

Present one complete proposed configuration for review: the full `.marc/config.json`, policy, and proposed guidance content, plus a table listing **every value**, including nested settings, defaults, derived absolute paths, optional omissions, tool pin, existing state/lock mappings, exception-file location and CI changes. Give the source/evidence and uncertainty for each. Include missing values explicitly. Summarize behavior changes, if any, and explain why each file exists. Never include secret values or private account details in tracked files.

For an explicit opt-in, show the updater's actual changed paths and explain why unrelated PRs become harder to review. Integration files can appear under `.marc/`, generated `scripts/quality/` files and `.agents/skills/marc-crew-*/` or `.claude/skills/marc-crew-*/` forwarding files. They remain sensitive where policy says so; do not promise approval-free upgrades. Recommend `autoUpdate: false` on the trusted target branch and a separate maintenance PR.

Before the full configuration confirmation, present one recommended list of members to create or extend, with source evidence, scope, companions, exclusions, validation and separate tooling prerequisites. Ask once whether I want you to create the recommended members using `skills/marc-crew-creator/SKILL.md` in the MARC source repository; accept a selected subset. If none are needed, say so. My acceptance authorizes the selected local source contributions without waiting for consumer configuration approval. It does not authorize publication or activation unless already explicitly included in my instructions. Existing-member activation and bundle upgrades are separate recommendations, not new-member creation. Missing values for consumer setup should not block bounded source authoring.

For an existing installation, replace the full first-install proposal and confirmation above with a focused before/after diff of additions and optional upgrades. Retain existing settings without reconfirmation. A no-change rerun requires no confirmation.

Ask me to confirm the complete first-install proposal, or just proposed configuration changes, manual upgrades and installation migrations on a rerun, and supply overrides for incorrect or missing values. Wait for my response before applying those proposals; additive forwarding-file repairs, explicitly opted-in PR intake updates and separately accepted source authoring follow their existing authorization. If I override a value, revise dependent values and show those revisions for confirmation. Do not silently treat elapsed time, inferred approval or an unrelated answer as confirmation. This confirmation requirement is part of this setup prompt.

After the corresponding authoring or configuration confirmation, implement only the accepted work:

- If member authoring was accepted, follow the crew creator skill in a separate MARC source checkout, preserving the consumer's pinned bundle. Prepare a reusable contribution with synthetic examples and no consumer identities, credentials, exceptions or operational state. Open the upstream PR when contribution publication is authorized; otherwise leave a reviewable local diff and PR draft. Track authoring, PR publication/acceptance and consumer activation separately. A draft member or open PR does not resolve the consumer's missing-expertise hold: complete the reviewed bundle pin, exact member version and area configuration through confirmed setup, then recapture affected review evidence before resuming assurance.
- If the contribution is pending or failing review/checks, save the consumer-local handoff defined in `docs/technology-discovery.md` and finish with its resumption instruction. Keep the trusted pin and existing authority; report missing-expertise limitations explicitly. Do not wait indefinitely, schedule unrequested polling, or activate a PR branch to bypass review. After verified merge and required checks, propose a full immutable bundle SHA containing the members, exact member versions, areas and forwarding updates. Confirm activation separately unless already authorized, then follow `docs/installation.md` and recapture affected evidence. A partial setup is not complete assurance.
- Create/update the consumer config, one authoritative policy and project/browser guidance. Prefer `.marc/policy.json` for new consumers; preserve legacy paths needed by existing launchers. Include governance/configuration/exception paths in sensitive-path rules. Keep required security, correctness and test gates and existing simple/full route semantics.
- Create a comment-only `.marc/gitleaksignore` from MARC's template when no file exists and point `scans.secretExceptions` at it. For an existing list, preserve its reviewed entries exactly and use the confirmed path. Check all workflow consumers before relocating it. Add no new accepted findings during setup.
- Wire CI to the confirmed pinned MARC version, consumer checkout/working directory, scanner version/checksum and sanitized artifact uploads. Set the explicit ignore-file configuration so the wrapper passes `--gitleaks-ignore-path`. Omit .NET/npm adapters for projects that do not use them; retain that project's actual CI checks. Leave the consumer's own analyzers, linters and quality tooling where they are and add no MARC configuration for them: their results belong to the consumer's build, and MARC requires only that the build succeeded. See [your own quality tools](configuration.md#your-own-quality-tools). Missing adapters or an unsupported provider require a visible implementation prerequisite, not skipped assurance.
- Make the Captain and crew discoverable through the chosen host's supported skill mechanism using the same pinned bundle. Preserve sibling references. Skills explicitly resolve consumer settings; they do not rely on automatic placeholder substitution. Do not install a floating or candidate-controlled skill version.
- Update the consumer README with setup/commands, paths, Gitleaks rationale, version selection and rollback. Keep secrets/account identifiers in private operational configuration. Do not move or delete existing state, release foreign locks, reset budgets, or rewrite historical reports.

Validate without merging: resolve config for the explicit consumer from another working directory; check tracked paths and policy protections; run focused shared/consumer tests; prove the scan wrapper receives the configured ignore file (an empty default must suppress nothing). Check CI checkout/history, scanner invocation and artifact-name wiring. Review the diff for accidental imported repository identities or exceptions. Do not execute candidate scripts with developer credentials. Use appropriate isolated checks, and distinguish mocked wiring, local scanner execution and hosted CI evidence.

Report created/changed files, final confirmed values, test results, any unresolved prerequisite and the exact next invocation. Do not claim hosted CI, external publication, merge, deployment or scheduling unless separately authorized and actually verified. Setup alone does not authorize an automatic merge run.
